# QCopilots Search development

- Application code is C++20 and Qt Widgets. All owned targets, programs, tests, packages and scripts use the `qcs` prefix. C++ namespace is `qcopilots_search`. Configuration variables use `QCOPILOTS_SEARCH_`.
- Never write generated build, dependency, test, model or package files into the source tree. Build roots and SDK roots are configurable. No developer-specific absolute paths in reusable code.
- Tests use unique QTemporaryDir roots, per-invocation working directories and explicit profile paths. Respect QCOPILOTS_SEARCH_TEST_ROOT. Fail explicitly when creation or cleanup fails. Never read or modify a real user profile in tests. Stop child processes and close files before cleanup.
- This checkout is shared by parallel agents. Edit only your assigned module. Subagents must not commit, switch branches, push, or overwrite other agents' files. The coordinating agent is authorized to commit and push codex/qcopilots-search-v1 for this implementation and its CI acceptance. Communicate interface changes before making them.
- Keep the application MIT notice and preserve attribution for adapted DigUp code. Third-party dependencies retain their licenses.
- Implement real behavior and explicit errors. Do not return fake embeddings or silently mark unsupported operations as completed.
- Documentation is primarily Chinese, with minimal semicolons. Reports distinguish executed tests from planned or unavailable tests.

- Keep the display name QCopilots Search, third-party names and stable non-path model/protocol identifiers unchanged. The canonical repository name is QCopilots-Search. The GUI target and executable are qcs-gui, while the product prefix, profile paths and other qcs programs remain stable. Do not add old command aliases.
- Third-party source files must remain identical to their locked upstream archives. Do not apply patches, rewrite downloaded sources or compile modified copies. Use upstream upgrades, project-owned build configuration and public API adapters. Keep generated configuration and source-cache metadata outside upstream source trees.
- Local development and check may use uncommitted changes. Record actual functional results and the working-tree state. CI uses a clean immutable commit and runs all retained tests and final package verification across all 11 native variants. Triggered or skipped checks are not passes. Record unavailable GPU hardware separately from CPU fallback validation.
- Release preparation selects packages from a successful CI run and attempt, verifies their source identity and checksums, and produces corresponding source materials. GUI acceptance uses the concise checklist in docs/testing.md, without a candidate evidence tree or CU recorder.
- Use the shared variant manifest for development, CMake, CI, package validation and release selection. Keep every variant and build configuration in separate external directories. Share only verified download and model caches, never incompatible compiler or backend caches.
- Semantic search accepts the normal cosine-ranked candidates, aggregates by file and combines with keyword results using RRF. Do not add relevance acceptance thresholds or production/test candidate modes. Keep model integrity, embedding dimensions and numerical regression checks.
- Each CI artifact is one verified installer or portable package uploaded as raw bytes with its stable filename. Keep diagnostics in native workflow logs. Source materials and optional symbols are generated independently. Release preparation verifies candidate, run, attempt, job and artifact identities before freezing assets. Upload and public publication are separate explicit commands. Publish only when requested by the user and after validating the exact clean main candidate, successful CI, tag and complete remote asset set.
- Routine package verification uses isolated external roots. Dedicated path tests also cover Unicode, spaces and long paths. Describe source-material coverage from its actual locks and archives, without claiming a complete offline GPU SDK source tree.
